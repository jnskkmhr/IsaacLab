# G1 on alpha moving MPM terrain

This standalone IsaacLab task places all robots on **one background terrain generated by `isaaclab.terrains`**. Each robot has its own bounded set of moving MPM particles and independent physics world. Particles that remain in simulated terrain retain their deformation and velocity. Recycled particles sample the shared terrain height and become fresh sand. Returning to a place does **not** restore previous tracks.

The environment, configuration, MDP, PPO, terrain adapter, and visualization code are local to this directory. The task does not inherit `g1_29dof_mpm` and does not modify core IsaacLab or Newton classes. Shared framework managers, robot assets, and general locomotion utilities are reused.

## Run

From the IsaacLab repository:

```bash
uv run --with wandb isaaclab train --rl_library rsl_rl \
  --task IsaacContrib-Velocity-Sand-G1-29dof-MPM-MovingPatch \
  --num_envs 1 --viz newton_gl

uv run --with wandb isaaclab play --rl_library rsl_rl \
  --task IsaacContrib-Velocity-Sand-G1-29dof-MPM-MovingPatch-Play \
  --num_envs 1 --viz newton_gl --checkpoint /path/to/model.pt
```

No trained policy is included. Train and Play use the same terrain pipeline; Play disables training randomization and uses a forward command. The robot starts on sand without an approach platform or retaining wall.

## Configuration

The runtime code lives in `env_cfg/`, `mdp/`, `util/`, and the two `mpm_env*.py` files. Tests, reports, and changelog fragments live under `dev/`. See [the refactor notes](dev/doc/refactor.md) for the configuration lifecycle and validation.

`MovingPatchTerrainCfg` in `util/terrain.py` defines particle-region dimensions, sampling, material, and sand depth. It is nested at `cfg.scene.terrain.moving_patch_terrain`. Background extent comes directly from `cfg.scene.terrain.terrain_generator`. Background placement and elevation come directly from the generated mesh. `cfg.scene.terrain` is a task-local subclass of IsaacLab's `TerrainImporterCfg`, using the standard `TerrainGeneratorCfg` and subterrain configurations. `G1PhysicsCfg` in `env_cfg/physics_cfg.py` declares solver choices and coupling. `mpm_env_cfg.py` defines timing, grid capacities, and environment spacing.

```python
from isaaclab.terrains.height_field.hf_terrains_cfg import HfPyramidSlopedTerrainCfg
from isaaclab_tasks.contrib.g1_29dof_mpm_moving_patch.mpm_env_cfg import G1MovingPatchEnvCfg_PLAY

cfg = G1MovingPatchEnvCfg_PLAY()
patch = cfg.scene.terrain.moving_patch_terrain
cfg.scene.num_envs = 4
cfg.scene.env_spacing = 4.0
patch.moving_terrain_size = (2.0, 2.0)
patch.boundary_terrain_size = 0.2
cfg.scene.terrain.terrain_generator.size = (20.0, 20.0)  # Per tile; default is one tile.
patch.voxel_size = 0.04
patch.particles_per_cell = 1.25
patch.material.friction = 0.7

# Optional: replace the default flat terrain with a standard IsaacLab generator.
cfg.scene.terrain.terrain_generator.sub_terrains = {
    "slope": HfPyramidSlopedTerrainCfg(slope_range=(0.1, 0.1), platform_width=0.5)
}
```

The following fields belong to `cfg.scene.terrain.moving_patch_terrain`:

| Field | Type | Meaning |
| --- | --- | --- |
| `moving_terrain_size` | `tuple[float, float]` | Simulated terrain width along X/Y [m] |
| `boundary_terrain_size` | `float` | Kinematic boundary width on **each side** [m] |
| `tracked_body` | `str` | Robot link name, resolved separately in each world |
| `particle_depth` | `float` | Vertical sand thickness below the generated surface [m] |
| `robot_spawn_height` | `float` | Root height above the sampled surface at spawn [m] |
| `shift_step` | `float` | Quantized patch movement distance [m] |
| `voxel_size` | `float` | MPM grid spacing [m] |
| `particles_per_cell` | `float` | IsaacLab sampling multiplier per voxel dimension |
| `jitter` | `float` | Existing IsaacLab `MPMGridCfg` jitter fraction in `[0, 1]` |
| `material` | `MPMParticleMaterialCfg` | Density, elasticity, friction, yield, damping, and other material values |
| `floor_thickness` | `float` | Thickness below the lowest support point when closing an open mesh [m] |
| `show_boundary_particles` | `bool` | Include boundary particles in rendering |
| `visual_color` | `tuple[float, float, float]` | Untextured background/emitter RGB color |

The complete particle region is `patch_size`, computed as `moving_terrain_size + 2 * boundary_terrain_size` in XY. Changing background size does not change particle count. Particle sampling follows IsaacLab's cell-centered `MPMGridCfg` convention.

The generator's `size` is the per-tile XY extent. The generated area is `(size[0] * num_rows, size[1] * num_cols)`; `border_width` adds a border outside it. These generator values are no longer overwritten by scene initialization. The default is one 20 × 20 m flat tile without a border. Robots use a regular grid controlled by `scene.env_spacing`; spawn heights are sampled from the background surface. Each complete particle patch must fit inside the generated terrain at its spawn position. Generated-terrain curriculum spawn origins remain disabled (`use_terrain_origins=False`).

The default `mpm_active_cell_count_per_world = None` now derives cell capacity from the final particle count, with leaf capacity as a minimum. Smaller moving terrain therefore reduces the dominant grid and coupling-buffer reservations. A positive integer still forces a fixed per-environment reservation. See [the capacity investigation and measured results](dev/doc/particle_capacity_scaling.md).

Sparse reservations remain configurable through `mpm_active_cell_count_per_world`, `mpm_leaf_node_count_per_world`, `mpm_lower_node_count_per_world`, and `mpm_upper_node_count_per_world`. They scale with the final `scene.num_envs`. These are **allocation limits**, not the measured number of occupied cells. See the [shared-terrain implementation and memory measurements](dev/doc/shared_terrain.md) before increasing them.

## Terrain and collision

| Region | Physics and storage | Rendering |
| --- | --- | --- |
| Simulated terrain | Positive-mass particles; implicit MPM and two-way foot coupling | Particle spheres |
| Boundary terrain | `ParticleFlags.ACTIVE`, zero mass/inverse mass; pinned to reference positions each physics substep | Optional particle spheres |
| Background terrain | One immutable generated surface; no background particles or history cache | One continuous visual mesh covering the background terrain |

The original generated surface supplies particle heights. Supporting ground is a copy shifted downward by `particle_depth`. Open meshes are closed below their lowest point so that MuJoCo can process them. The coupled solver requires exclusive shape ownership, so the same support geometry has **two global collider instances**: one owned by the MPM solver and one owned by the rigid solver. This count stays two regardless of the number of environments. Both are hidden; the sand-level background is visual only.

Boundary particles still participate in MPM and provide mechanical support. MPM is not restricted to particles touching a foot. Hiding particles only changes rendering.

The standard viewer renders the original generated mesh at `/World/visual_terrain/terrain`, using the shared Ground_080 texture/material. Collision is explicitly disabled on this mesh. It renders every triangle, including beneath the moving particle patch. This visual-only mesh has no collision effect, but it can visually cover particles below its surface. GPU height queries and supporting colliders still use the original generated terrain geometry.

There is one particle batch, `/model/particles`, using the standard viewer's default appearance and physical radii. Task-local viewer subclasses filter selected environments and optional boundary particles before logging that batch. The GUI **Show Particles** checkbox controls it; disabling particles restores a continuous background. `particle_color` in the GL/RTX visualizer configuration overrides the standard particle color. The old `/moving_patch/env_*/sand` batches were removed, so enabling the checkbox no longer duplicates particles. See [rendering details and screenshots](dev/doc/particle_visualization.md).

Supported terrain must have a valid top surface at every sampled XY position. Downward ray queries select the topmost hit; caves, overhangs, and holes are not represented as multiple sand layers. Missed height queries raise an error. Default flat and generated slope terrain have been tested; arbitrary generator combinations still need validation.

## Physics-step integration

1. IsaacLab generates the shared terrain, samples robot spawn heights, and replicates robots and particle grids into independent Newton worlds.
2. IsaacLab builds the ordinary coupled solver. `G1MovingPatchEnv.load_managers()` then creates `self.moving_patch_particle` using `self.scene.terrain.cfg.moving_patch_terrain` and `self.scene.terrain.background_mesh`. It resolves the tracked link in each world and stores reference positions, original masses, initial plastic-volume values, and fixed GPU arrays.
3. Before each coupled physics substep, the patch center follows the robot in increments of `shift_step` and is clamped to the shared background bounds.
4. Particle reference XY positions wrap into the outer particle region. A changed reference XY or an environment reset triggers a **GPU query against the shared surface**. The sampled height plus the particle's reference depth determines its fresh position.
5. Retained simulated particles keep their physical state. Recycled particles, boundary-to-simulated transitions, escaped particles, and selected-world resets restore fresh state. Boundary particles have zero mass/inverse mass and stay pinned.
6. When masses change, the adapter refreshes MPM view masses and derived density, clears numerical warm-start data, and runs the coupled solver. It pins boundary positions and velocities afterward.

| State | Fresh value |
| --- | --- |
| `particle_q` | Wrapped reference XY and sampled surface height plus reference depth |
| `particle_qd` | Zero |
| `mpm:particle_qd_grad` | Zero |
| `mpm:particle_elastic_strain` | Identity |
| `mpm:particle_Jp` | Stored initial value |
| `mpm:particle_stress` | Zero |
| `mpm:particle_transform` | Identity |

Height sampling during physics does not transfer per-particle heights between CPU and GPU. The existing small changed-mass/error counter readback remains, so this is not a fully asynchronous graph-captured path. The local visualizer filters and compacts particles on the GPU, with one visible-count readback for the standard renderer.

The installed Newton version does not expose a particle-property refresh API. The local adapter updates `solver._mpm_model` density using `mass / reference_volume`. Radii, reference volumes, flags, material coefficients, and collider membership stay fixed. This compatibility code must be checked when updating Newton. Clearing numerical warm starts affects the combined solve, while retained physical particle state in other worlds remains unchanged.

Selected robot roots reset above the generated surface sampled at their actual reset XY. Selected-world particle resets defer patch reconstruction until the next physics substep, after robot forward kinematics updates. Timing follows IsaacLab's `sim.dt`, policy `decimation`, and coupled-entry substeps. CUDA graph capture remains disabled for this local task.

Final terrain and sparse-capacity updates run in `G1MovingPatchEnvCfg.validate_config()`, called by IsaacLab's standard `cfg.validate()` before environment creation. This applies CLI/Hydra overrides made after construction. A standalone script that needs the final emitter or capacity values should call `cfg.validate()` after changing settings. Capacity helpers are in `util/solver_setting.py`.

## Non-flat terrain

The scene includes `flat` and `waves` entries. Flat terrain remains the default (`flat.proportion=1.0`, `waves.proportion=0.0`). The wave entry uses IsaacLab's `HfWaveTerrainCfg` with `amplitude_range=(0.2, 0.2)` [m] and `num_waves=4`. The generator selects one terrain type per tile; enabling both gives random selection, not a mixture of heights. With the default single tile, set flat to zero and waves to one as shown below. The previous 5 cm, two-wave preset was visually subtle across 20 m. The new preset has a 0.5 m flat perimeter so height-field edge correction stays inside the mesh boundary. See [rendering performance and wave verification](dev/doc/texture_cache_and_waves.md). Initial and recycled particles sample the background mesh at their own world XY positions. The support collider uses the same shape shifted down by `particle_depth`; the sand thickness is vertical, not measured along the surface normal. This supports flat, sloped and wave surfaces that have one height at each XY position. It does not model caves or stacked terrain layers. Steep slopes or steps may need different particle/grid resolution and material settings to remain stable.

```python
terrains = cfg.scene.terrain.terrain_generator.sub_terrains
terrains["flat"].proportion = 0.0
terrains["waves"].proportion = 1.0
```

## Separate visual and support terrain

`env_cfg/scene_cfg.py` declares two terrain entries:

```python
visual_terrain: TerrainImporterCfg = TexturedTerrainImporterCfg(
    prim_path="/World/visual_terrain",
    collision_group=-1,
    terrain_type="generator",
    disable_collider=True,
    use_terrain_origins=False,
)
terrain: BackgroundTerrainImporterCfg = BackgroundTerrainImporterCfg(
    prim_path="/World/ground",
    disable_visual=True,
    # Particle, generator, and support settings are configured here.
)
```

`TexturedTerrainImporterCfg` is a task-local subclass of the standard `TerrainImporterCfg`; it only adds texture coordinates and a portable preview material alongside MDL. Standard GL/RTX scene rendering draws `/World/visual_terrain/terrain/mesh`. There are no manual background `log_mesh()` calls. The visual terrain has collision disabled through the standard importer option.

`BackgroundTerrainImporter` stores the original surface as a Warp mesh for particle height queries and imports two lowered support colliders: `/World/ground/terrain/mesh` for MJWarp and `/World/ground/mpm_support/mesh` for MPM. It contains no background rendering or texture setup. `disable_visual=True` hides the support geometry through the standard importer. A viewer's collision-debug display can still show hidden colliders.

The two entries initialize from the shared `GENERATOR` in `scene_cfg.py`. If overriding geometry after configuration construction, apply the same generator settings to both entries. An explicit seed and the task-local `SeededTerrainGenerator` reproduce geometry for both entries, including subterrain functions that use NumPy's global random state. The original random state is restored after generation. The entry named `terrain` supplies environment origins and particle reset heights regardless of declaration order. The visual importer is available as `scene["visual_terrain"]` and cannot replace the primary terrain. `collision_group=-1` registers both as shared global scene geometry.

Visual settings now belong to `scene.visual_terrain`:

| Previous particle-terrain field | Current setting |
| --- | --- |
| `show_background` | `visual_terrain.disable_visual` (inverted boolean) |
| `background_material` | `visual_terrain.visual_material` |
| `background_texture` | `visual_terrain.color_texture` |
| `background_texture_scale` [m/repeat] | `visual_terrain.texture_repeat_per_meter` [repeat/m], its reciprocal |

The standard importer now honors `disable_collider` and supports `disable_visual` for generated meshes, USD terrain, and planes. Both default to false, preserving normal terrain rendering and collision.

The task uses the generated terrain at its original position and height; `background_origin` and `surface_height` are removed. Particle emitter heights run from `-particle_depth` to zero relative to the surface. All task Warp functions and kernels remain in `util/kernel.py`.
